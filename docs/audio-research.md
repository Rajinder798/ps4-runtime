# Guest AudioOut PCM through the SDL disk sink

Gate: G4 audio-path increment, not hardware playback or completion of G4. The
original `audio-pattern` PS4 homebrew submits synthetic stereo PCM through real
guest AudioOut services. The pinned shadPS4 process converts/queues it through
its SDL backend, whose built-in disk device writes host PCM. The host independently
checks channel-specific frequencies, their order, amplitude bounds and surrounding
silence. This does not establish audible speaker/headphone output, device
selection, latency, codec/AJM decoding, multichannel audio or commercial gameplay.

## Fixture and verification

The [source](../research/homebrew/audio_pattern/main.cpp) reads a four-period
permutation plus a test mode from `/app0/audio.bin`, initializes user/audio
services and opens the main AudioOut port as 48 kHz S16 stereo with 256-frame
buffers. It submits 192 buffers per phase (49,152 frames), in this order:

1. Silence.
2. Different square-wave fundamentals in the left and right channels.
3. A second different pair of channel-specific fundamentals.
4. Silence, then drain, a bounded tail wait and port close.

The four reviewed periods are 64, 96, 128 and 192 guest frames, corresponding to
750, 500, 375 and 250 Hz. Each run permutes them. Peak guest sample amplitude is
2,000 of 32,768. All samples are generated by original integer code; no audio
asset, decoder library or song is used. Each AudioOut call/close is checked for
failure. The guest emits ordered submission/completion markers, then sleeps for
supervisor termination. Natural process exit and API timing conformance remain
unverified.

The harness requires the exact reviewed source/converted ELF
[contract](../config/audio-pattern.json), unchanged strict engine/patch/header/tree
checks, zero unresolved imports, actual guest entry and all four ordered phase
markers. It allocates a new portable session and verifies the staged fixture.
The pinned strict build has `SDL_DISKAUDIO=ON`; no engine patch or newly packaged
dependency is needed. The engine still constructs its usual Vulkan host path, so
its existing Vulkan prerequisites/diagnostics remain required for this audio test.

Only the launched supervisor/engine receives these process-local SDL hints:
`SDL_AUDIO_DRIVER=disk`, `SDL_AUDIO_DISK_OUTPUT_FILE=<new session>/sdl-output.raw`,
`SDL_AUDIO_DISK_TIMESCALE=1`, `SDL_AUDIO_FREQUENCY=48000`, `SDL_AUDIO_CHANNELS=2`
and `SDL_AUDIO_FORMAT=F32LE`. The parent environment is preserved. The engine's
retained SDL device-open diagnostic must name that exact file, F32LE, two channels
and 48 kHz. This is a real SDL output device implementation, selected as a research
sink. It does not read a microphone or capture unrelated system audio. No host or
guest prepares the PCM result file; the pinned SDL disk driver writes it downstream
of the actual guest service and engine backend.

After completion and confirmed Job Object tree cleanup, the host verifies raw
frame alignment, a 16 MiB file bound, finite bounded samples and a 3–12 second
frame-count bound. It uses a Goertzel projection independent of the guest's
integer square-wave generator. Each expected channel fundamental must contribute
at least 65% of window energy, with RMS between 0.005 and 0.15. Silence requires
RMS below 0.00001. Analysis windows contain 6,144 frames and overlap by half;
four consecutive matching windows span 15,360 frames (0.32 s). Sustained silence,
the first stereo pair, the second pair and final silence must appear in order.
This is a defined signal-presence/channel/order test, not bit-exact PCM validation,
full-stream dropout/quality certification or a latency/performance benchmark.

Silent and swapped-channel negative inputs alter only the fixture's staged mode
byte. They still complete the real guest API sequence and produce well-formed
SDL PCM, but must fail the independent normal-signal requirements. Thus guest
logs and successful AudioOut returns alone cannot establish audio output.

## Reproduce

Use the existing Windows x86-64, Python 3.12+, verified compiler/OpenOrbis SDK,
strict engine and Vulkan host. No physical controller or recording device is needed.

```powershell
python tools/build_homebrew.py --sample audio-pattern --llvm-bin build/tools/llvm-mingw-20261006-ucrt-x86_64/bin --inspector build/native/ps4-runtime.exe
python tools/run_audio_research.py --engine build/upstream/windows-x64-strict/shadPS4.exe --engine-report build/upstream/strict-evidence/strict-build.json --fixture build/homebrew/audio-pattern/audio_pattern.oelf --supervisor build/native/ps4-startup-supervisor.exe --output build/audio/single-new
python tests/audio_guest_tests.py --engine build/upstream/windows-x64-strict/shadPS4.exe --engine-report build/upstream/strict-evidence/strict-build.json --fixture build/homebrew/audio-pattern/audio_pattern.oelf --supervisor build/native/ps4-startup-supervisor.exe --hello-world build/homebrew/hello-world/hello_world.oelf --service-roundtrip build/homebrew/service-roundtrip/service_roundtrip.oelf --videoout-pattern build/homebrew/videoout-pattern/videoout_pattern.oelf --pad-videoout build/homebrew/pad-videoout/pad_videoout.oelf --output build/audio/acceptance-new
```

Choose new output directories. Visual Studio puts native helpers under `Release/`.
`--audio-case silence|swapped` selects a genuine guest-generated negative signal;
neither may pass normal audio-sink verification. The single run retains
`audio-result.json`, strict audit, host/engine diagnostics and the raw PCM file.
The raw file is headerless F32LE interleaved stereo, not a WAV file.

The acceptance script checks two normal runs, the two negative signals, and real
regressions for all four earlier fixtures. All eight cases require actual guest
entry, guest completion, zero unresolved imports and confirmed cleanup. It also
checks the parent environment is unchanged and the disk sink did not leak into
earlier sessions. The [filtered local evidence](../research/results/2026-10-18-audio.json)
records source/input/PCM/audit hashes, measured analysis windows/RMS and pass/fail
outcomes. Complete raw data remains local under `build/audio/acceptance-001`.
Hosted source builds and host tests are separate results in the PR.

The fifteenth CTest suite, `audio-evidence-contract`, has six portable tests using
independently generated sine waves: correct sequence, silence/swapped/reversed/mono
rejection, absent silence/transient/wrong challenge rejection, bounded PCM/format
validation, strict phase/failure ordering and pre-execution prerequisite failure.
Those generated files are host tests, not guest evidence. The 20-test startup suite
also binds the fifth fixture's source/ELF and checks actual child-process environment
isolation on Windows. The hosted homebrew workflow builds all five fixtures and
uploads only build/symbol metadata, without SDK/fixture/audio binaries.

## Diagnostics, limits and release holds

SDL prints its selected disk-driver and file-format diagnostics at critical/error
severity. These two expected lines are retained and required as sink evidence;
they are not suppressed or treated as an AudioOut failure. The pinned
`sceUserServiceInitialize` dummy-initialization warning remains, as do earlier
optional asset/font/module, PT_INTERP/SCE and Vulkan host format/extension messages.
The AudioOut implementation's trace label includes `STUBBED`, despite the queued
implementation exercised here; this result establishes only the tested PCM path,
not complete AudioOut initialization, drain, close or format conformance.

New source is original GPL-2.0-or-later. SDL's existing disk backend is reused in
the separate engine; no SDL/engine code is copied into the inspector. No engine,
SDK, fixture/game binary, audio asset, firmware or key is committed/uploaded.
The [dependency/source/relink and runtime/resource review holds](release-audit.md)
still block engine redistribution. Windows 10, hardware playback, alternate devices,
OpenAL, microphone input, surround/downmix, guest codecs, physical controllers,
natural PS4 guest exit remain unverified. The fixture stays outside the two
registered launch IDs; there are no new audio Settings controls. Subsequent
[combined graphics/input/PCM](interactive-research.md) and
[engine window-close](window-shutdown.md) results cover those separate boundaries.
Hardware output remains a functional dependency before full G4 completion.
